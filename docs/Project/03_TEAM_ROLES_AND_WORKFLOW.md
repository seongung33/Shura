# Shura 팀 역할 및 협업 방식

## 1. 운영 원칙

두 개발자가 게임의 공통 기반을 함께 설계하고 구현한다. 한 사람이 전체 게임 틀을 만들고 다른 사람이 기능만 얹는 구조를 피한다. 콘텐츠 담당도 단순 문서 담당이 아니라 Unity 데이터 입력, UI, 테스트, 영상과 제출까지 실제 결과물에 참여한다.

팀원 이름은 확정 후 아래 `담당자` 칸에 기입한다.

## 3. 매일 협업 리듬

### 시작 회의 — 10분

- 어제 완료한 것
- 오늘 반드시 끝낼 것 한 가지
- 막힌 것
- 같은 파일 또는 씬을 건드리는지 확인

### 개발 중

- 기능 브랜치에서 작업한다.
- 2시간 이상 막히면 Discord `버그제보` 또는 개발 채널에 공유한다.
- 기능이 완전히 커지기 전에 작은 단위로 커밋한다.
- 외부 에셋과 AI 사용 내역은 작업 직후 기록한다.

### 종료 회의 — 15분

- 각자 실행 화면을 공유한다.
- `develop` 통합 빌드를 한 번 실행한다.
- 다음 날 우선순위를 정한다.
- 일정표와 결정 기록을 갱신한다.

## 4. Git 브랜치 규칙

| 브랜치 | 용도 |
|---|---|
| `main` | 실행 가능한 안정·제출 버전 |
| `develop` | 팀 작업 통합 |
| `feat/*` | 기능 개발 |
| `fix/*` | 버그 수정 |
| `docs/*` | 문서만 수정 |

브랜치 예시:

```text
feat/player-movement
feat/enemy-spawner
feat/skill-synergy
feat/network-spike
fix/web-build-input
docs/game-guide
```

## 5. 작업 시작 절차

```bash
git switch develop
git pull
git switch -c feat/작업이름
```

작업 완료 후:

```bash
git add .
git status
git commit -m "feat: 구현 내용"
git push -u origin feat/작업이름
```

GitHub에서 `feat/* → develop` Pull Request를 만들고 다른 팀원 한 명이 확인한다.

## 6. Unity 충돌 방지 규칙

- `Main.unity`는 그날 정한 통합 담당자 한 명만 수정한다.
- 개발자 A는 `PlayerTest.unity`에서 기능을 검증한다.
- 개발자 B는 `CombatTest.unity`에서 기능을 검증한다.
- 콘텐츠 담당은 `ContentTest.unity`에서 UI와 에셋을 배치한다.
- 재사용할 오브젝트는 Prefab으로 전달한다.
- 파일 탐색기에서 에셋을 이동하지 않고 Unity의 Project 창에서 이동한다.
- `.meta` 파일을 삭제하거나 제외하지 않는다.
- Unity 버전을 임의로 업그레이드하지 않는다.
- 같은 ScriptableObject 데이터 파일을 동시에 수정하지 않는다.

## 7. 완료의 정의

기능은 다음 조건을 만족해야 완료로 인정한다.

- Unity Console에 새 빨간 오류가 없다.
- 기능을 재현하는 테스트 씬 또는 Main 씬에서 실행된다.
- 다른 팀원이 Pull 후 실행해봤다.
- 임시 값과 알려진 제한을 문서 또는 PR에 적었다.
- 외부 에셋·AI 사용이 있다면 해당 기록을 남겼다.
- `develop`에 병합된 뒤에도 Play가 정상 작동한다.
