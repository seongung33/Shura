# Shura 팀 역할 및 협업 방식

> 마지막 역할·계약 정리: **2026-08-10 KST**. 진행 상태는 `12_CURRENT_PROJECT_STATUS.md`에서 관리한다.

## 1. 운영 원칙

기존 코드의 작성자가 누구였는지와 관계없이, 2026년 7월 29일부터 아래 담당자를 기능 소유자로 정한다. 기능 소유자는 코드 작성뿐 아니라 프리팹·데이터 연결, 테스트, 관련 문서 갱신까지 책임진다.

담당 영역은 분리하지만 게임 시작, 스킬, 라운드가 실제 한 판에서 이어져야 하므로 공개 API와 공용 프리팹 구조는 함께 합의한다.

## 2. 역할 분담

### 진미리 — 게임 진입·멀티플레이·전체 통합

게임을 실행한 순간부터 플레이어가 실제 전투에 입장할 때까지의 전체 흐름과 최종 통합을 맡는다.

- 초기화, 시작 화면과 메인 메뉴
- 방 생성·참가·퇴장 UI
- `MainMenu → MultiPlayerEntry → MultiPlayerLobby → Main` 정식 흐름과 레거시 `NetworkTest` 회귀 경로 유지·개선
- 참가 후 네트워크 플레이어 생성과 소유권 적용
- 일반 `Player.prefab` 기능과 `NetworkPlayer.prefab` 구조 통합
- 준비 완료 또는 게임 시작 조건과 게임 씬 진입
- 연결 실패, 중복 참가, 정상 퇴장과 재접속 처리
- Main 씬 통합과 씬 전환
- Windows/Web 빌드와 빌드 오류 점검
- 스킬·적·라운드·승패 결과의 네트워크 동기화 통합

**완료 기준:** 게임 실행 → 방 생성 또는 참가 → 두 플레이어 표시 → 실제 게임 씬 입장까지 끊기지 않고 진행된다.

### 이재준 — 캐릭터·스킬·전투 성장

스킬 기획이 확정되면 데이터와 실행 코드를 만들고, 최종 디자인이 없어도 게임에서 사용할 수 있는 상태까지 구현한다.

- `SkillData`와 스킬 프리팹 제작·연결
- 초기 유도 투사체는 `SkillRunner`, 주몽 직선·장판·버프형 스킬은 `ISkillBehaviour` 계약으로 실행
- 새 실행 방식은 기존 계약을 복제하지 않고 호환 지점을 먼저 합의
- 캐릭터 고유 액티브의 입력, 쿨다운 또는 충전과 효과
- 스킬 대상 탐색, 피해, 범위와 지속 효과
- `IDamageable` 기반 피해 연결
- 캐릭터별 시작 스킬과 스킬 데이터 입력
- 경험치 레벨업 후 스킬·강화 선택
- 스킬 HUD, 쿨다운 표시와 임시 시각 피드백
- 7속성 기록과 플레이어 간 연계 반응

**완료 기준:** 기획된 스킬을 ScriptableObject와 프리팹으로 설정할 수 있고, 테스트 씬과 실제 게임에서 발동·피해·쿨다운·성장을 확인할 수 있다.

### 문성웅 — 맵·15분 라운드·적·아이템·게임 종료

게임에 입장한 뒤 0분부터 15분까지 진행되는 한 판 전체를 맡는다. 회복·자석 등 맵에서 획득하는 아이템도 같은 드롭·라운드 흐름 안에서 구현한다.

- 전투 맵과 플레이 가능 영역
- 0~15분 라운드 타이머와 시간 구간별 몬스터 생성
- 생성 수, 종류, 체력과 난이도 증가
- 일반 몬스터, 추가 패턴 몬스터와 최종 보스
- 15분 조건과 보스 처치에 따른 클리어 판정
- 캐릭터 한 명이 사망했을 때 패배 처리
- 승리·패배 결과, 전투 정지와 재시작
- 회복 아이템과 경험치·아이템 자석
- 추가 획득 아이템의 스폰·드롭·습득·효과
- 적과 아이템 프리팹·데이터, 라운드 밸런스
- 라운드 타이머, 보스와 결과 HUD

**완료 기준:** 임시 그래픽으로도 0분에 시작해 시간에 따라 적이 변하고, 15분 보스와 승리 또는 캐릭터 사망과 패배로 한 판이 종료된다.

### 통합 경계와 최종 책임

| 연결 지점 | 최종 책임 | 협업 규칙 |
|---|---|---|
| 게임 씬 입장과 플레이어 생성 | 진미리 | 생성된 플레이어에 이재준의 스킬 구성과 문성웅의 라운드 등록이 적용되어야 한다 |
| 기본·특수·액티브 스킬 | 이재준 | 유도 투사체는 `SkillRunner`, 주몽 스킬은 `ISkillBehaviour`, 모든 피해 수신은 `IDamageable` 계약을 유지한다 |
| 적 생성과 적 프리팹 | 문성웅 | 이재준의 스킬이 찾을 수 있도록 `Enemy` 레이어와 `IDamageable` 구조를 유지한다 |
| 플레이어 체력 컴포넌트 자체 | 진미리 | 네트워크 플레이어 통합과 소유권을 책임지고 `PlayerHealth.IsDead`와 `onDeath` 공개 계약을 유지한다 |
| 플레이어 사망에 따른 패배 판정 | 문성웅 | 현재 `GameManager`는 `PlayerHealth.IsDead`를 확인한다. 향후 이벤트 방식으로 바꾸면 진미리와 함께 계약을 갱신한다 |
| 스킬·라운드 네트워크 동기화 | 진미리 | 각 기능 담당자가 동기화할 판정 데이터를 정의하고 진미리가 네트워크 흐름에 연결한다 |
| 경험치 구체와 레벨 수치 누적 | 이재준 | 레벨업 선택과 스킬 성장까지 연결한다 |
| 회복·자석·필드 아이템 | 문성웅 | 플레이어 능력치나 스킬에 영향을 주면 이재준과 효과 계약을 합의한다 |
| Main 씬과 최종 빌드 | 진미리 | 다른 담당자는 프리팹·데이터·테스트 씬 단위로 전달하고 Main 씬 동시 편집을 피한다 |

공개 API나 공용 프리팹 구조를 바꿔 다른 담당 영역에 영향을 주는 경우 먼저 공유한다. 특히 `SkillRunner`, `IDamageable`, `PlayerHealth.IsDead`·`onDeath`, `Enemy` 레이어와 `Player` 태그는 일방적으로 변경하지 않는다.

### 공통 작업

별도의 콘텐츠·QA 전담자는 두지 않는다. 각 담당자가 자기 기능의 임시 에셋·데이터·테스트와 관련 문서를 함께 책임진다.

- 진미리: 메뉴·방 UI, 네트워크·씬 통합·빌드 테스트
- 이재준: 캐릭터·스킬 데이터, 스킬 UI와 임시 효과
- 문성웅: 맵·적·보스·아이템 데이터와 임시 에셋
- 전원: 코드 리뷰, 통합 플레이 테스트, 버그 재현, 에셋 출처와 AI 사용 기록
- 제출 영상과 PDF의 최종 편집 담당자는 촬영 전에 별도로 정한다.

### 병렬 작업과 통합 순서

세 명이 같은 기능을 기다리지 않고 다음 순서로 병렬 진행한다.

1. 진미리는 테스트용 플레이어라도 방 입장 후 생성되는 흐름을 먼저 고정한다.
2. 이재준은 `PlayerTest` 또는 `SkillTest`에서 네트워크 없이도 스킬·액티브·성장을 완성한다.
3. 문성웅은 `CombatTest` 또는 `StageTest`에서 네트워크 없이도 타이머·스폰·보스·아이템·승패를 완성한다.
4. 각 기능이 단독 테스트를 통과하면 프리팹과 데이터 단위로 진미리에게 전달한다.
5. 진미리가 Main 흐름에 연결한 뒤 세 명이 두 PC 통합 테스트를 한다.

진미리가 모든 기능 내부를 대신 구현하는 것은 아니다. 네트워크 연결 중 스킬 또는 라운드 로직 자체의 수정이 필요하면 해당 기능 담당자가 수정하고, 진미리는 동기화와 씬 연결을 맡는다.

### AI를 활용한 개발 작업

생성형 AI는 구현 초안, 구조 설명, 오류 분석과 테스트 항목 정리에 사용하는 개발 도구다. AI가 완성된 코드 형태를 제안했더라도 기능의 소유권과 최종 판단은 담당자에게 있다.

1. 담당자가 기능 목적, 기존 코드 계약, 수정 범위와 완료 조건을 정한다.
2. AI에 관련 파일과 금지 사항을 제공하고 구현안 또는 진단을 요청한다.
3. 제안된 코드가 기존 구조를 중복하거나 공개 API를 깨뜨리지 않는지 검토한다.
4. 담당자가 Unity에서 씬·프리팹·Collider·Inspector·ScriptableObject 참조를 연결한다.
5. Play Mode 또는 네트워크 테스트를 수행하고 실제 결과를 확인한다.
6. 오류가 있으면 원인을 좁혀 수정안을 다시 검토하며, 검증하지 않은 코드를 완료 처리하지 않는다.
7. Git 커밋과 함께 AI 도구, 요청 목적, 산출물, 사람의 통합·검증 내용을 `06_AI_USAGE_TECHNICAL_DOCUMENT.md`에 기록한다.

코드가 수정 없이 채택된 경우에도 “사람이 코드를 다시 작성했다”고 표현하지 않는다. 대신 요구사항 정의, 채택 판단, Unity 연결, 테스트와 통합에서 수행한 작업을 구체적으로 기록한다.

## 4. Git 브랜치 규칙

| 브랜치 | 용도 |
|---|---|
| `main` | 실행 가능한 안정·제출 버전 |
| `develop` | 팀 작업 통합 |
| `feat/*` | 기능 개발 |
| `fix/*` | 버그 수정 |
| `docs/*` | 문서만 수정 |

브랜치 예시:

```text
feat/player-movement
feat/enemy-spawner
feat/skill-synergy
feat/network-spike
fix/web-build-input
docs/game-guide
```

## 5. 작업 시작 절차

```bash
git switch develop
git pull
git switch -c feat/작업이름
```

작업 완료 후:

```bash
git add .
git status
git commit -m "feat: 구현 내용"
git push -u origin feat/작업이름
```

GitHub에서 `feat/* → develop` Pull Request를 만들고 다른 팀원 한 명이 확인한다.

## 6. Unity 충돌 방지 규칙

- `Main.unity`와 게임 진입 씬은 통합 담당인 진미리가 수정한다.
- 진미리는 정식 `MainMenu → MultiPlayerEntry → MultiPlayerLobby → Main` 흐름을 먼저 검증하고, `NetworkTest.unity`는 레거시 회귀 비교에만 사용한다.
- 이재준은 기존 `PlayerTest.unity` 또는 별도 `SkillTest.unity`에서 스킬을 검증한다.
- 문성웅은 `StageTest.unity`에서 웨이브·보스·아이템을 검증한다. `CombatTest.unity`는 현재 구성이 불완전하므로 복구 전 정본 테스트로 사용하지 않는다.
- 아직 없는 `SkillTest.unity`를 만들 경우 `Scenes/Tests` 아래에 둔다.
- 재사용할 오브젝트는 Prefab으로 전달한다.
- 파일 탐색기에서 에셋을 이동하지 않고 Unity의 Project 창에서 이동한다.
- `.meta` 파일을 삭제하거나 제외하지 않는다.
- Unity 버전을 임의로 업그레이드하지 않는다.
- 같은 ScriptableObject 데이터 파일을 동시에 수정하지 않는다.

## 7. 완료의 정의

기능은 다음 조건을 만족해야 완료로 인정한다.

- Unity Console에 새 빨간 오류가 없다.
- 기능을 재현하는 테스트 씬 또는 Main 씬에서 실행된다.
- 다른 팀원이 Pull 후 실행해봤다.
- 임시 값과 알려진 제한을 문서 또는 PR에 적었다.
- 외부 에셋·AI 사용이 있다면 해당 기록을 남겼다.
- `develop`에 병합된 뒤에도 Play가 정상 작동한다.
